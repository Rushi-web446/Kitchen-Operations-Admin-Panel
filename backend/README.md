## Description

[Nest](https://github.com/nestjs/nest) framework TypeScript starter repository.

## Project setup

```bash
$ npm install
```

## Compile and run the project

```bash
# development
$ npm run start

# watch mode
$ npm run start:dev

# production mode
$ npm run start:prod
```

## Run tests

```bash
# unit tests
$ npm run test

# e2e tests
$ npm run test:e2e

# test coverage
$ npm run test:cov
```

## Deployment

When you're ready to deploy your NestJS application to production, there are some key steps you can take to ensure it runs as efficiently as possible. Check out the [deployment documentation](https://docs.nestjs.com/deployment) for more information.

If you are looking for a cloud-based platform to deploy your NestJS application, check out [Mau](https://mau.nestjs.com), our official platform for deploying NestJS applications on AWS. Mau makes deployment straightforward and fast, requiring just a few simple steps:

```bash
$ npm install -g @nestjs/mau
$ mau deploy
```

With Mau, you can deploy your application in just a few clicks, allowing you to focus on building features rather than managing infrastructure.

## Observability

In production applications, observability is essential for understanding how your system behaves, detecting issues early, and maintaining reliable performance.

[NestJS Observe](https://observe.nestjs.com) automatically instruments your NestJS application, giving you deep visibility into your system with minimal setup:

- **Distributed tracing:** Follow requests across services and understand how they flow through your system.
- **Waterfall analysis:** Visualize request execution and identify slow operations, bottlenecks, and unexpected delays.
- **Performance analysis:** Analyze application performance in real time and quickly pinpoint areas that need optimization.
- **Metrics:** Track key application and infrastructure metrics to understand system health and performance trends.
- **Logging:** Centralize and correlate logs with traces and other telemetry to make debugging easier.
- **Error tracking:** Detect errors quickly and investigate their root causes with the surrounding context.
- **SLA monitoring:** Track service-level objectives and identify when your application is approaching or exceeding defined thresholds.
- **Alarms and alerts:** Set up alerts for critical errors, performance degradation, SLA violations, and other anomalies so your team can react quickly.

## Financial model and billing

The backend resolves pricing by company tier, not by trusting incoming client totals.

- Companies may assign an explicit price tier; if not, the system falls back to the single default tier.
- Dish and option prices are resolved via the existing PriceTier/DishPrice/OptionPrice models using the configured pricing rule.
- Derived tier pricing is allowed and then rounded up to the next 5 cents using Decimal arithmetic.
- Order creation snapshots the calculated unit prices and line totals, so changing a catalogue price does not mutate historical orders.
- Confirmed, uninvoiced orders are billing candidates for admin invoice creation.
- Each invoice belongs to exactly one company and its total is calculated from confirmed order totals. Once issued, the invoice is immutable and can only transition to PAID.
- Invoice status lifecycle is `ISSUED -> PAID`.

## Dispatch and Driver Workflow

A Delivery Drop is one physical delivery that may contain multiple confirmed orders. Orders are grouped into a Drop when company, canonical delivery address, and exact delivery time match. Address snapshots are normalized for case and whitespace; recipient/contact fields do not affect the address key. The database's composite unique key and a transaction-scoped advisory lock prevent duplicate groups when dispatchers refresh or group concurrently.

Drop lifecycle:

```text
KITCHEN_READY -> DISPATCH_READY -> OUT_FOR_DELIVERY -> DELIVERED
```

Dispatch can group only confirmed orders with `kitchenReadyAt` set. A new Drop inherits the company's default driver when that driver belongs to the same company. Dispatch may reassign a driver before delivery starts. `OUT_FOR_DELIVERY` requires a same-company assigned driver. Driver endpoints derive the Driver profile from the authenticated JWT user; clients cannot select another driver identity.

On-time delivery is defined as `deliveredAt <= scheduled deliveryAt`. Scheduled delivery time is constructed from the Drop's delivery date/time in Asia/Kolkata. No grace period is applied. The optional delivery note and photo URL are stored on the Drop; image bytes are not stored in PostgreSQL.

Dispatch API:

- `POST /api/dispatch/drops/group` with optional `{ "deliveryDate": "YYYY-MM-DD" }`
- `GET /api/dispatch/drops` with optional `deliveryDate`, `status`, `companyId`, and `driverId` filters
- `POST /api/dispatch/drops/:id/ready`
- `POST /api/dispatch/drops/:id/assign-driver` with `{ "driverId": 123 }`
- `POST /api/dispatch/drops/:id/out-for-delivery`

Driver API:

- `GET /api/driver/drops/today`
- `POST /api/driver/drops/:id/deliver` with optional `{ "note": "Delivered to reception", "photoUrl": "https://..." }`

The schema has no canonical DeliveryAddress entity, so the implementation uses a stable SHA-256 key derived from the existing address snapshot. A Driver profile is required to be assigned to the same Company as its Drop. Orders retain `CONFIRMED` status during `OUT_FOR_DELIVERY` because their existing lifecycle has no separate in-transit Order status; their `outForDeliveryAt` timestamp is set, and they become `DELIVERED` atomically when the Drop is delivered.
